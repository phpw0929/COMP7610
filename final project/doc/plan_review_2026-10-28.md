## 4. 产品方案的答题质量审核

| 问题 | 目前方案的回答 | 报告/演示必须避免的过度表述 |
| --- | --- | --- |
| 解决谁的问题 | 机构签发、志愿者查看、第三方跨机构验证；角色与闭环清楚。 | 没有用户调研证据时不宣称已被机构采用。 |
| 为什么用区块链 | 多方可独立读取签发、撤销和更正历史；减少对单个运营界面或私有数据库的依赖。 | 普通数据库也能做审批；要承认成本、公开性和管理信任的取舍，不能只说“不可篡改所以更好”。 |
| 链上动作是否有意义 | 机构批准产生新的可验证记录，状态机和权限约束有业务后果。 | 连接钱包、展示地址或仅查询数据不算完成 R05。 |
| 设计与实现是否一致 | 分钟、UTC date、Claim/Record 状态分离、自动签发、更正关联均按实际 Solidity 规划。 | 不再介绍 NFT mint、活动编辑、任意管理员改写记录等不存在的流程。 |
| 是否能证明真实服务 | 只能证明某个授权钱包签发的内容与历史；机构核实出勤仍是现实流程。 | 不宣称链自动判断出勤、证明真人身份或消除机构造假。 |
| 是否完全去中心化 | 记录查询和历史可独立核验，但管理员认可机构、钱包密钥、RPC/metadata 服务仍存在信任与可用性依赖。 | 不宣称“完全去中心化”“无法作恶”“无任何单点”。 |
| 隐私如何处理 | 不把个人联系方式、照片和证明全文上链；公开钱包、时间、状态和哈希。 | 不把 hash 描述为加密，不把公开钱包数据描述为匿名或自动合规。 |
| 规模与经济性 | 小规模课程 demo、无 token/支付、用户发送写交易需要测试 ETH。 | 无实测不写吞吐/成本优势；不将 Sepolia demo 当作生产上线。 |
| 贡献与结果是否可信 | 用实际 commit、文件、测试与媒体证据说明成员贡献。 | 不虚构测试通过、部署验证、访谈、性能数值或贡献比例。 |

结论是选题能回答“为什么做、为什么链上、怎样实现和怎样验证”，关键是把这些回答落实到真实 UI 与报告证据，而不是继续扩充功能数量。
